Allure Hybrid Local Pipeline

Reference images and a brief go in. A structured SceneSpec, an automatic Blender build, and a 3D walkthrough the client opens in the browser come out. All of it on one laptop, built on the scene engine that already runs.

Verdict. Keep the DPR's local-first deployment and SceneSpec contract, adopt the Phase 1 diagram's eleven stages as the pipeline's stage names and state machine, and build on top of the existing patch-based scene engine rather than beside it.

Hard rules carried over from the DPR

  1. No raw prompt ever reaches Blender. Blender reads build_manifest.json only.
  2. The web Scene with its patch pipeline and validator stays the single system of record. Blender is a consumer.
  3. Reuse a local asset before generating. Procedural before Meshy.
  4. Every stage writes a checkpoint file. Resume finds the last complete checkpoint.
  5. No API request blocks on analysis or rendering. Everything long is a job.

04Data model

SceneSpec = Scene plus four additions

Keep the existing conventions: meters, +Y up, −Z forward, yaw in radians. Every addition is optional with a default so current scene files still load.

class StyleSpec(BaseModel):
    name: str                      # "modern_warm_minimal"
    tags: list[str]
    palette: list[str]             # hex
    materials: list[str]           # material_ids from app/materials
    lighting_mood: Literal["warm_daylight","cool_daylight","evening","studio"]

class LightingSpec(BaseModel):
    mood: str
    sun_azimuth_deg: float = 135
    sun_elevation_deg: float = 40
    exposure_ev: float = 0.0
    interior_lights: list[InteriorLight] = []

class CameraPlan(BaseModel):
    type: Literal["walkthrough","orbit","stills"] = "walkthrough"
    duration_seconds: int = 45
    seconds_per_room: float = 8
    keyframes: list[TourKeyframe] = []          # filled by walkthrough planner
    hero_shots: list[SavedView] = []

class Scene(...):                 # existing fields, plus:
    spec_version: str = "1.0"
    style: Optional[StyleSpec] = None
    lighting: Optional[LightingSpec] = None
    camera_plan: Optional[CameraPlan] = None

class SceneObject(...):           # existing fields, plus:
    source_strategy: Literal["local_asset","local_modified","procedural","generated"] = "procedural"
    material_overrides: dict[str, str] = {}     # slot -> material_id

The DPR's example SceneSpec, which is Z-up in degrees, is the shape of the Blender manifest, not the canonical scene. Conversion is one function: (x, y, z) → (x, −z, y) and rotation_y radians → rotation_euler.z degrees.

Intelligence outputs

  • DesignAnalysis: intent, rooms with dimensions or estimated: true, constraints, furniture spotted in photos, confidence.
  • StyleSpec: as above.
  • ObjectPlan: category, semantic type, room, priority, approximate dimensions, style notes, relation.
  • AssetPlan: object id, strategy, asset id, material overrides, procedural params or generation prompt.
  • ValidationReport: errors, warnings, readiness.
  • AgentInput / AgentOutput envelopes exactly as DPR §8.

SQLite and project storage

data/allure.db holds projects, inputs, analyses, scene_specs (pointer rows to the JSON scene and version), jobs, events, outputs. Asset and material registries stay JSON. Project files follow the DPR §20 layout under data/projects/{project_id}/; a checkpoint is simply the presence of a stage's output file.

Job mechanics (app/jobs/, built in M1)

  • Job{job_id, project_id, type, lane, status, attempt, max_attempts, checkpoint, error, params, result, log_path, …} with status QUEUED, RUNNING, SUCCEEDED, FAILED or RETRYING.
  • Two worker lanes as thread pools started in the FastAPI lifespan: ai (2 threads, network-bound) and render (1 thread, owns the GPU). Blender runs as a subprocess from the render lane with output teed to logs/.
  • Failures retry from the last checkpoint and never rebuild earlier stages. A render failure re-runs at the preview profile first.
  • Every transition writes an event row. The UI polls GET /projects/{id}/events?after=.
  • On startup the runner resumes every job that was still in flight, logging a resumed event. Tested: retry-from-checkpoint and restart-resume both pass.
  • When hosting arrives, the same job rows can be claimed by a remote worker. Nothing in the API changes. This is the diagram's box 4 without a broker.

07Intelligence layer (app/intelligence/)

class IntelligenceProvider(Protocol):
    def analyze_input(self, bundle: InputBundle) -> DesignAnalysis: ...
    def create_style_spec(self, analysis: DesignAnalysis) -> StyleSpec: ...
    def plan_objects(self, analysis, style, catalog_summary) -> ObjectPlan: ...
    def validate_scene(self, scene: Scene) -> ValidationReport: ...
  • Mock provider is deterministic: keyword rules from the description, palette from image average colours, rooms from dimensions or defaults. Runs with zero API keys. Tests and the golden project use it.
  • Gemini provider extends the existing adapter with inline image parts, a response schema, one stage-specific prompt per call, one JSON repair retry, then per-stage fallback to mock with a warning in the output envelope.
  • Agents never emit coordinates. They produce zones, priorities and relations. The existing design planner turns those into positions and commit_patch validates. This is the DPR's "no raw text to Blender" rule applied one layer earlier.

Asset decision order, per object

  1. Catalog search with a real model within ±15 % of planned dimensions → local_asset.
  2. Same asset with scale within ±25 % or a material override → local_modified.
  3. Semantic type in the procedural set (bed, rug, wardrobe, lamp, TV unit, shelf, table, seat, plant, box) → procedural. These are exactly today's web primitives, so both renderers agree.
  4. Otherwise generated, only when a Meshy key is set and the object is flagged unique. The build proceeds with a procedural stand-in and swaps when the asset validates.

Scripts are pure functions of the manifest: no network, no business logic. Each stage saves scene.blend so a later failure resumes from the file. The runner in app/blender/runner.py (built in M0) builds the command, streams output to a per-job log, enforces a per-profile timeout, and parses the final ALLURE_RESULT line from stdout.

The camera path reuses the existing guided-tour keyframes (room order via doors, pans to the three largest objects). Blender only smooths and renders them, so the web tour, the panorama nodes and the video follow the same route.

Three more scripts serve web delivery: render_panoramas.py (equirect camera at each keyframe), bake_lightmaps.py (UV2 unwrap, Cycles bake per object, atlas per room) and export_web_scene.py (glTF export with KTX2 textures and Draco geometry, plus tour.json).

13Assumptions made

Say so if any of these is wrong; each one changes a milestone.

  1. Blender 5.2.1 LTS is the target version: the build installed on this machine.
  2. Gemini stays the first real provider. The diagram's "GPT-6 Astra" is covered by the provider interface.
  3. Meshy generation stays off by default and is not needed for the first end-to-end demo.
  4. SQLite is introduced only for projects, inputs, jobs, events and outputs. Scene and asset registries stay JSON.
  5. The primary deliverable is the in-browser walkthrough: the 360° panorama tour first, then the baked real-time scene. The 1080p Eevee MP4 is a secondary export. No Cycles video.
  6. The cinematic photo-to-film route stays optional and untouched.
